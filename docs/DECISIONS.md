# Decisions

Append newest at the bottom. Format: date, decision, reason, evidence, what would change it.

- 2026-10-17 REPOS Two repos: `omarchy-widgets` (code, schemas, reference docs) and this one (site, registry, versioned docs). Reason: different contributors, trust and cadence; registry PRs come from strangers. Would change if the registry needs to be consumed by other tools independently (split it out).
- 2026-10-17 STACK SvelteKit (Svelte 5) + adapter-static + TypeScript, bun, mdsvex + shiki + pagefind for docs, self-hosted JetBrains Mono and Geist. Reason: requested stack; same font families omarchy.org loads (verified in its stylesheet). Would change: docs tool if custom glue exceeds about two days, fall back to Starlight (see PLAN.md section 7).
- 2026-10-17 REFERENCE Omarchy site studied for pattern only (layout, tokens, 22 theme palettes, coverflow picker, plugins marketplace UX). Palette values saved in `docs/reference/omarchy-org-theme-tokens.json`. No stylesheet, markup, images, video or music copied.
- 2026-10-17 SCAFFOLD SvelteKit 3: configuration lives in the `sveltekit({...})` Vite plugin options (flat, no `kit` namespace, no `svelte.config.js`); tsconfig extends `$app/tsconfig`. TypeScript is pinned to 5.9 because TypeScript 7 (native) has no JS API and SvelteKit and svelte-check need it. Static CSP is emitted as a `<meta>` tag with a script hash (verified in build output). Actions are pinned by commit SHA (checkout 7.0.1, setup-bun 2.2.0, upload-artifact 7.0.2). `bun audit` clean.
- 2026-10-17 THEMES (M0b) 22 themes in `src/lib/themes/themes.ts` use the public palettes from the reference JSON; our token names; `--border` is derived (45% from `--bg` toward the official strong border, because the official hairlines are nearly invisible on several themes), `--brand-soft` is `--bg` with 14% brand and `--selection` `--bg` with 32% brand (both computed at build time, no colour maths in the browser). `src/lib/themes/css.ts` resolves tokens and emits `src/lib/themes/themes.css` and `static/theme-boot.js` via `bun run themes:gen` (part of `bun run build`); both generated files are committed and a unit test fails if they drift. Contrast rules (text 7:1, muted 4.5:1, brand-ink on brand 4.5:1, brand on bg 3:1) are enforced by `bun run themes:check` and unit tests. Extra rule we added: `--muted` must also reach 4.5:1 on `--surface` (it is used on boxes).
- 2026-10-17 THEME ADJUSTMENTS Smallest lightness shift (0.5% HSL steps, away from the page background), no theme dropped: rose-pine `--text` #575279 -> #544f73 (7:1) and `--brand` #56949f -> #4b7e89 (3:1 on bg, brand-ink 4.5:1); everforest `--muted` #918f84 -> #a4a297 (4.5:1 on surface); miasma `--muted` #8c8c82 -> #8e8e84 (4.5:1 on surface). The list is printed by `bun run themes:check`. Would change: if upstream palettes change, regenerate and re-check.
- 2026-10-17 BOOT The theme is applied before first paint by `static/theme-boot.js`, a plain external `<script src>` in `app.html` (allowed by CSP `script-src 'self'`, no inline script). It reads `ow-theme` from localStorage (try/catch, validated against the known ids), else `prefers-color-scheme` (light gives catppuccin-latte, otherwise tokyo-night). Its id list is generated from `themes.ts`. Only an explicit choice is stored, so people who never choose keep following their system.
- 2026-10-17 PICKER Deviation/clarification: browsing in the picker applies a theme live but only Enter or "Keep this theme" persists it; Esc, Cancel or any other close reverts to the theme the page had when it opened. Reason: otherwise Enter and Esc would mean the same thing. The "Press T" hint is dismissed by its button or by opening the picker, remembered in `ow-theme-hint`. The `$lib` alias is not available in this SvelteKit 3 setup, so imports are relative; internal links use `resolve()` from `$app/paths` (lint rule). Stub pages added for /widgets/, /docs/, /security/ and /contribute/ so header and footer links work.
- 2026-10-17 DESKTOP (M1) The home hero is `src/lib/components/Desktop.svelte`: real widget components (`components/widgets/`, tokens only; a unit test scans them and Desktop.svelte for `#hex`, `rgb(`, `hsl(` and similar) on a CSS-only pixel field. The pure model is `src/lib/desktop/layout.ts`: 8px grid, edge and neighbour guides within 6px, per-type size classes (compact, wide, tall, large) from the code repo brief section 6, sizes clamped to the nearest valid class size and never rejected, nudge and resize helpers, remove-to-tray, undo and redo (100 steps), reset. Layout is in memory only: not persisted, "Reset layout" is one click. Resize handles are east, south and the corner (no north or west) to keep position and size changes independent.
- 2026-10-17 SAMPLE DATA The widgets read one shared store (`src/lib/desktop/sample.ts`, seeded PRNG, readable store) that ticks once a second only while subscribed, the tab is visible and reduced motion is off; otherwise a still frame. The sample clock is a fixed sample time, not the real time, so prerender and hydration match and nothing is read from the machine. PR rows use `example/` repositories. The page says in one `data-sample` note that the data is sample data. Widgets that throw show an error card through `svelte:boundary`.
- 2026-10-17 DESKTOP A11Y AND MOTION Outside edit mode widgets are `inert`. In edit mode each is a focusable group (arrows move 8px, Shift+arrows resize, Delete removes, Ctrl/Cmd+Z undo, Ctrl/Cmd+Shift+Z redo, Esc leaves) and every action is announced in an `aria-live="polite"` region; focus moves to the next widget, the restored widget or the Edit button, never to the body. Below 720px the desktop is a static wrapped arrangement with a note that editing needs a larger screen. The staggered entrance runs only under `prefers-reduced-motion: no-preference`; axe tests run with reduced motion so mid-animation opacity cannot cause false contrast failures. The surface is capped at 784px wide so the default layout (designed for 720) never leaves a large empty field.
- 2026-10-17 REGISTRY-TRUST Tier comes only from `registry/review/<id>.json` with `reviewedCommit` equal to the listing commit; listing schema has `additionalProperties: false` and no trust field; stale reviews are ignored and stated in the output. Otherwise `spec`/`community`; fixtures are `concept`. Reason: strangers write listings. Would change: signed review attestations.
- 2026-10-17 REGISTRY-FETCH The build fetches only `manifest.json` and `widget.json` from `https://raw.githubusercontent.com/<owner>/<repo>/<commit>/` (https, exact host, no userinfo/port/query, `redirect: 'error'`, 10 s, 256 KB enforced while streaming, JSON only, no auth). It never executes widget code. Fixture (concept) entries read `registry/fixtures/` and need no network, so CI stays offline for them.
- 2026-10-17 REGISTRY-SCHEMA `registry/schema/widget.schema.json` is a hand-made DRAFT v0 from the PROJECT_BRIEF sketch (`PINNED.json` version `draft-0`). Draft additions: provider `auth: none|vault` (so the access summary can say a secret is needed; the widget still never holds it). Replace with the pinned release of the code repo's `spec/widget.schema.json` when it exists.
- 2026-10-17 REGISTRY-OUTPUT `dist/index.json` has no timestamp (reproducible builds). Widget text is plain text only (control/format characters stripped, lengths capped, HTML-looking text rejected); no markdown is rendered in this milestone. Loader uses `import.meta.glob` so `svelte-check` passes before `dist` exists.
- 2026-10-17 REGISTRY-FIXTURES Seven concept listings point at `https://github.com/dexterhere/omarchy-widgets` with commit `000...0`; they are labelled "concept, not installable" and never fetched.
- 2026-10-17 REGISTRY-TIER-FIX widget.json `tier` is author controlled, so it no longer decides anything: `core`, `verified` and `spec` all require a matching review record (same id, `reviewedCommit` equal to the listing commit); otherwise `community`, with `declaredTier` kept as information and labelled "declares itself spec, not reviewed". Reason: a stranger could self-assert "spec".
- 2026-10-17 REGISTRY-NAMESPACE `io.github.<owner>.*` ids must match the repo owner; other namespaces need `registry/namespaces.json` (maintainer managed). Review records, namespaces and `MAINTAINERS.json` are CODEOWNERS paths and CI (`scripts/check-review-changes.ts`) fails PRs touching them unless the author is in the base branch's `MAINTAINERS.json`.
- 2026-10-17 REGISTRY-SPOOFING Strings and keys in all fetched data are rejected, not stripped, when they contain Cc, Cf, Zl or Zp characters or look like HTML; `__proto__`, `constructor` and `prototype` keys are rejected; setting defaults capped at 200. Output ids are re-checked before any file write. A Codex review of an older ref did not report on redirects, size/time caps, prototype pollution, id-as-filename traversal or duplicate ids; each now has an explicit test in `tests/unit/registry.*.test.ts`.
- 2026-10-17 CI-GATE (security hook) The maintainer gate no longer reads a list from the PR working tree. Maintainers come from the BASE branch; if the file does not exist there (a fresh staging or main before the first promotion) a list hardcoded in the script (`BOOTSTRAP_MAINTAINERS`) is used; every other failure yields nobody (fail closed). Known limit: the script itself is checked out from the PR head, so a PR that edits it could bypass the gate. CODEOWNERS covers `/scripts/` and `/.github/`, but with a single maintainer GitHub cannot require a second approval, so the real control is the maintainer reading every PR that touches those paths. Would change with a second maintainer (require code-owner review) or by running the gate from the base branch in a `pull_request_target` workflow (not done: it has its own risks).
- 2026-10-17 E2E The preview port is configurable with `PW_PORT` (default 4173) so parallel worktrees do not reuse each other's stale preview server; network-host assertions use the same value.
